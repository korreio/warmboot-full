# Admitting reusable lessons

Start from the target's actual constraints and existing owner. A useful source lesson
is input to a decision, never permission or a replacement authority.

1. Inspect the relevant source and establish ownership, licence and permitted use.
2. Extract only the smallest useful behavior; avoid private inventories and captured
   outputs. Keep required third-party notices with retained expression or data.
3. Record `ADOPT`, `MERGE INTO EXISTING`, `CITE ONLY` or `OMIT`, with the surviving
   owner, concrete applicability, evidence limits, recurring cost and revisit trigger.
4. Validate the changed behavior and obtain independent review before acceptance.

New technology needs a reason tied to the target, primary-source research where
applicable, a bounded comparison and failure/recovery analysis. Familiar precedent is
not universal proof. Do not import credentials, user data, private paths or outside
project status. Source access and publication each need their own authority.

The [capability catalog](capability-sources.json) binds current local design rationale;
the [sample manifest](../examples/MANIFEST.json) classifies the shipped samples.
The [licence map](../LICENSING.md) records the applicable licence and required notices.

Bounded history inspection follows `routes/context.md`; every `git diff`
form remains excluded and no source lesson grants Git mutation authority.
